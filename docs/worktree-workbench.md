# Worktree 工作台

每个 Worktree 保存自己的会话、文件、Diff 标签、分屏布局、焦点和右侧栏状态。选择项目、Worktree 或已有会话会进入对应 Worktree；同一个 Worktree 内切换会话会激活原标签，已有文件缓冲区继续保留。

在底部状态栏可以切换两种界面。两种界面都将会话与编辑器的标签分开，并一起跟随当前 Worktree 文件夹：

- **经典界面**：会话与文件分为两列，支持列宽调整和最大化。各列显示自己的当前分组，其他分组保留在同一个状态层。
- **新界面**：左侧只显示已打开项目及其 Worktree，复用现有打开、克隆和创建项目操作。主工作区与右侧栏顶部共用一行外层 Worktree 标签。会话和编辑器各有自己的标签区域，在各自区域内支持拖动排序、移动到另一个分组、左右或上下分屏。文件和 Diff 共用编辑器标签栏。每个区域独立记住选中标签和分屏比例，调整一边不会改变另一边。

外层标签的固定区位于左侧，临时标签使用斜体。每个标签提供固定、取消固定、关闭和操作菜单；右侧 **+** 创建新的空标签。可以同时保留多个临时或空标签，取消固定不会关闭其他临时标签。选择已打开的 Worktree 优先激活它的现有标签；选择新的 Worktree 会填入当前未固定标签，或在当前标签固定时追加临时标签。关闭或替换外层标签只改变导航，不销毁该 Worktree 的会话、文件、分屏和右侧栏状态。

空标签显示项目选择提示，隐藏并禁用保留的会话、编辑器、右侧栏与终端内容，不创建自动草稿。Ctrl/Cmd+W 关闭这个空外层标签；新建会话、切换/恢复内部标签、保存和关闭全部文件的内容快捷键会被拦截。普通 Tab 焦点导航以及全局搜索、设置和打开文件夹仍可使用。异步文件请求在开始时导航，之后的完成事件不会重新填入新选中的空标签。

会话历史按钮位于会话标签栏左侧，支持当前 Worktree 与整个项目的历史搜索。选择历史会话会先确认外层导航成功，再打开内部会话。全局聊天使用独立的具体范围，不等同于空标签。

外层导航缓存使用客户端后端/窗口命名空间，保留固定、临时和空标签。上限为 4096 个标签、4 MiB 缓存载荷；达到标签上限时禁用 **+** 并显示容量提示，打开新 Worktree 无法追加时提示错误并保留原范围。激活已有标签、复用临时标签和取消固定仍然可用。

在标签上右键可以分屏、移动、关闭当前标签或合并分组。空分组可以点击聚焦，随后打开的同类标签进入该区域的分组。窄窗口显示焦点分组，并保留完整分屏树。

文件的未保存标记显示在标签上。同一物理路径的文件在一个客户端后端内共享缓冲区，关闭其中一个工作区引用不会销毁其他引用中的内容。关闭最后一个未保存文件引用会要求确认。

布局和右侧栏使用带版本的客户端本地缓存。未保存文件以及不能从路径重建的会话/冲突 Diff 使用本地 IndexedDB 恢复副本。读取缓存失败时不会用空状态覆盖原数据；恢复不可用时工作台会提示保存未保存的文件。

客户端保存工作台状态，现有会话 `opened_tabs` 协议继续同步会话。完整布局跨设备同步仍需后续独立协议。

## 开发验证

```sh
pnpm lint .
pnpm test
pnpm build
```

主要回归覆盖工作区隔离、混合拖动排序、会话绑定后的稳定持久化身份、未保存内容恢复、外部冲突重载、共享文件保存、延迟请求取消和右栏的延迟文件夹切换。

## macOS 开发构建

`.github/workflows/macos-workbench-build.yml` 支持手动指定分支和 ARM/Intel 架构，也会在专用 `build/workbench-*` 分支提交后运行。构建在 macOS runner 上产生 `.app.zip` 和 `.dmg`，生成 SHA-256 清单并上传为 GitHub Actions artifact。

手动触发时可以填写可选的 `product_name` 和 `bundle_identifier`。推送触发时，工作流会从 HEAD 提交的 `Build-Product-Name` 和 `Build-Bundle-Identifier` Git trailer 读取同样的临时运行时覆盖；这些值只写入 `RUNNER_TEMP` 中传给 `pnpm tauri build --config` 的 JSON，不修改 `src-tauri/tauri.conf.json` 或正式发布配置。覆盖 JSON 同时关闭更新包生成并使用 ad-hoc 签名。

每个构建把构建提交、目标架构、结果、下载地址、校验和和已验证的 bundle 信息写入独立 `ci-receipts/workbench/<commit>/<target>/<attempt>` 分支。这些回执可通过已有 Git SSH 权限读取，方便没有 API 令牌或匿名 API 限流的开发环境取得结果。

回执中的 `build_commit` 是 CI 实际 checkout 的提交。`source_commit` 只在构建提交包含 `Workbench-Source-Commit` trailer 时出现，用来指向已经验证过的源提交；控制器可以用同树的构建专用提交携带临时构建元数据，而不把开发版名称或 bundle identifier 写入产品配置。CI 会独立解析 `source_commit` 并比较 `source_commit^{tree}` 与 `HEAD^{tree}`；对象缺失或树不一致时构建失败，不上传可信 artifact。上传 artifact 里的 `bundle-info.json` 和回执都会记录 `provenance`，包含构建提交/树、可选源提交/树、对象是否解析成功、树是否一致和身份结果。`bundle-info.json` 还记录 `CFBundleName`、`CFBundleIdentifier`、主可执行文件的 `lipo` 架构、目标架构以及 `.app.zip`/`.dmg` 的 SHA-256。

开发构建使用 ad-hoc 签名，正式分发的 Developer ID 签名、公证和更新签名由原发布流程负责。
